# M1.3 Netty Direct Buffer Lifecycle & Memory Safety

## Buffer Allocation Strategy
The native encoding pipeline requires direct, off-heap memory to allow zero-copy parsing and serialization across the JNI boundary.

1. **Thread-Local Staging Buffer**:
   - Allocated once per thread via `ThreadLocal<ByteBuffer>`.
   - Capacity: **262,144 bytes (256 KB)**.
   - Lifecycle: Cleared at the beginning of each packet serialization. Never reallocated or closed during normal runtime.
   - Memory Model: Direct off-heap memory.

2. **Netty Output Buffer**:
   - Allocated via Netty's `PooledByteBufAllocator.DEFAULT.directBuffer(capacity)`.
   - Sized dynamically to $\max(65536, \text{stagedLen} + 1024)$.
   - Passed to native code via direct pointer address (`address()`).
   - Native code writes wire payload directly into off-heap memory.
   - Java code advances `writerIndex(bytesWritten)`.

## Shadow Mode Lifecycle & Zero-Leak Guarantees
In SHADOW mode:
1. Native `directBuf` is populated and compared byte-by-byte against `javaPayload`.
2. Native `directBuf` is unconditionally released via `directBuf.release()` immediately following comparison.
3. Reference count decreases from 1 to 0; memory is immediately returned to Netty's chunk pool.
4. Java reference buffer is transmitted and subsequently released by Netty's downstream pipeline.

## Error Recovery Lifecycle
If JNI or Rust encoding returns a negative error code or panics:
1. Exception/panic handler catches the event.
2. `directBuf.release()` is invoked immediately in a `finally` or error block.
3. Fallback to Java reference buffer proceeds without memory leakage or lingering unreleased handles.
