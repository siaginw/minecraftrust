# External candidate decisions

Reviewed 2026-09-26 against source baseline `c4b868db2c9e4b03f745bf93c6ebf4fd8a8519e7`.

This is the H18/H19/H22.5.I/H27 decision inventory: **70 candidates, including all 48 named H22.5 requirements**. It does not complete the experiments or the hardening program. All performance judgments below are hypotheses; no benchmark numbers are invented. The [machine ledger](../../machine/external-reuse/ultra-candidates.json) carries exact versions, source URLs, activity observations, component licenses, notices, risks and acceptance plans for each row.

No production dependency, packet-authority setting, compression backend, MCK6 behavior or program milestone is changed by these artifacts. No dependency was installed for this ledger. Prototype versions are exact **planned targets**, not statements that experiments ran. Resolve and record transitive/native versions, checksums, features and toolchain in an isolated experiment receipt before execution. Mutable source-study refs are dated observations, not reproducible build pins.

The one existing implementation reference is [cafebabe H1 cross-check](../../machine/external-reuse/classfile-crosscheck.json), pinned there to 0.9.0. Its supplements and existing evidence remain owned by H1. This ledger neither rewrites that evidence nor claims to have revalidated it.

## How to use the decisions

- **PROTOTYPE** selects a bounded comparison with a scalar/current-path oracle. It does not authorize production adoption. There are 35 candidates in this category, not 35 completed experiments.
- **STUDY** keeps a serious option under review without adding a dependency; 25 entries.
- **BORROW_ALGORITHM** means independent implementation against an explicit semantic specification, without copying upstream implementation; 5 entries.
- **AVOID** rejects integration for the stated scope and records why; 5 entries.
- **ADOPT** requires evidence for a bounded scope. There are no unsupported ADOPT decisions in this research inventory.

Priorities rank the next useful evidence, not a mandate to install everything. P1 starts with correctness/observability and the smallest complete-path comparisons. P2 adds targeted comparators after that baseline. P3 is conditional research or an alternative retained for a specific future gap.

## Recommended sequence

1. Establish transformed-class qualification and first-divergence replay evidence. Reuse the existing H1 cafebabe experiment; compare typed JNI lifetimes at one narrow new boundary. Bind loader, descriptor, transformed identity, receiver assumptions and effects before considering an intrinsic.
2. Instrument real capture/admission/commit/fallback paths and retained bytes. Use bounded labels and full-path latency distributions. Profile Java callbacks on a supported host before selecting any hot method.
3. Compare custom SoA against hecs, then the required bevy_ecs/Shipyard comparators. Prototype generation handles, bounded communication and immutable catalog publication with cancellation/reclamation tests.
4. Compare scalar palette/chunk logic to independently specified algorithms and stable SIMD candidates. Include complete serialization and slow-consumer retention, not just a fast inner loop.
5. Run isolated NBT, compression, allocator and sidecar experiments only against equivalent correctness and durability conditions. MCA/NBT compatibility and MCK6 stay unchanged.

The practical layout remains dense 4096-cell section arrays with uniform/small-palette/dense representations where measurements justify them. Blocks do not each become ECS entities. Entity logical identity includes generation and world/session incarnation; hot fields can use dense SoA storage while cold mod extensions remain separately addressed. Slot reuse is not permanent identity. A compatibility owner orders arbitrary Forge callbacks and RNG-visible effects; workers receive qualified immutable snapshots and return bounded effects for validated, ordered commit. Rayon or an ECS scheduler supplies execution machinery, not Minecraft semantics.

## Boundaries that materially change the decision

**Server substitutions.** Valence, Pumpkin, Hyperion, FerrumC and Temper are useful architecture sources. Their gameplay, plugin models and modern protocol targets do not establish execution of transformed Forge Java mods. FerrumC and Temper remain separate records: reviewed FerrumC code is MIT, while current Temper code is GPL-3.0. Folia provides region-ownership lessons, but its independent region timelines and plugin threading rules require compatibility changes; those cannot be imported invisibly. [Valence](https://github.com/valence-rs/valence), [FerrumC](https://github.com/ferrumc-rs/ferrumc), [Temper](https://github.com/temper-mc/temper), [Folia architecture](https://docs.papermc.io/folia/reference/overview/).

**Protocol versions.** Minecraft 1.12.1 is protocol 338 and 1.12.2 is protocol 340; their data versions are 1241 and 1343 respectively. The keepalive field changes between those protocol schemas, so shared block data must not collapse versioned packet adapters. This is a wire-format cross-check, not proof of Forge behavior. [Version inventory](https://github.com/PrismarineJS/minecraft-data/blob/master/data/pc/common/protocolVersions.json), [338 schema](https://github.com/PrismarineJS/minecraft-data/blob/master/data/pc/1.12.1/protocol.json), [340 schema](https://github.com/PrismarineJS/minecraft-data/blob/master/data/pc/1.12.2/protocol.json).

**JVM strategy.** Keep a mature embedded JVM as the compatibility path. The current decision is **DO NOT BUILD CUSTOM JVM without H19 adversarial semantic and strategic proof**. Ristretto VM and ristretto_classfile are separate choices. Espresso is an interpreter/runtime project; Crema is distinct experimental Native Image runtime-loading work. Neither the presence of class loading nor opcode support proves coremod transformations, reflection, JNI, object identity, monitors, exceptions and lifecycle compatibility. Oracle's similarly named Ristretto compiler discussion must not be confused with the Rust theseus-rs project. [Rust Ristretto](https://github.com/theseus-rs/ristretto), [Espresso architecture](https://github.com/oracle/graal/blob/master/espresso/docs/how-espresso-works.md), [Crema initiative](https://github.com/oracle/graal/issues/11327), [Crema progress](https://github.com/oracle/graal/discussions/13851).

**Licenses.** The machine ledger separates wrapper/native and component licenses. Pumpkin server code is GPL-3.0 while its plugin API crate is MIT OR Apache-2.0; the latter does not relicense the server. Folia API/server patches are covered by their GPL-3.0 patch license, and Starlight is LGPL-3.0. Valence's MIT code does not grant reuse of its separately licensed logo. Graal's component table distinguishes Espresso GPL-2.0, SubstrateVM GPL-2.0 with Classpath exception, and Truffle/SDK UPL-1.0; Oracle commercial distributions require separate review. OpenJ9's VM license is distinct from the OpenJDK class library. No GPL/LGPL implementation code is copied or mechanically translated here. [Pumpkin manifest](https://github.com/Pumpkin-MC/Pumpkin/blob/master/Cargo.toml), [plugin API](https://github.com/Pumpkin-MC/Pumpkin/blob/master/crates/pumpkin-plugin-api/Cargo.toml), [Folia patch license](https://github.com/PaperMC/Folia/blob/ver/26.2.x/PATCHES-LICENSE), [Starlight license](https://github.com/PaperMC/Starlight/blob/fabric/LICENSE), [Graal component licenses](https://github.com/oracle/graal/blob/master/README.md), [OpenJ9 contributions/licenses](https://github.com/eclipse-openj9/openj9/blob/master/CONTRIBUTING.md).

Native and binding licenses are also distinct for libdeflate (MIT native / Apache-2.0 wrapper), zlib-ng (Zlib native / dual MIT-Apache binding), RocksDB (Apache-2.0 OR GPL-2.0 native / Apache-2.0 wrapper), jemalloc (BSD-2-Clause native / dual MIT-Apache wrapper), rpmalloc (MIT native / dual MIT-Apache wrapper) and Tracy (BSD-3-Clause native / dual MIT-Apache client). Bundled dependency licenses must be resolved from each eventual experiment artifact; these entries are not a release-wide SBOM. The machine entries link the corresponding primary license texts and package metadata.

**Toolchain and operating systems.** The reviewed standard-library `std::simd` API remains nightly-only; use stable pulp/wide comparisons first. simdnbt's reviewed master has nightly/64-bit assumptions; check the exact pinned release before execution. Compio's IOCP path makes it relevant to Windows, while Monoio's Linux focus is a reason to defer a second runtime. async-profiler is a supported-host HotSpot experiment, not a claim of native Windows availability. [std::simd](https://doc.rust-lang.org/std/simd/index.html), [simdnbt source](https://github.com/azalea-rs/simdnbt/blob/master/simdnbt/src/lib.rs), [Compio](https://github.com/compio-rs/compio), [async-profiler](https://github.com/async-profiler/async-profiler/blob/master/README.md).

**Correctness before timing.** NBT experiments must preserve unknown mod tags, tag distinctions and modified UTF8. mmap requires an enforced immutable-file lifetime. Sidecar stores must be rebuildable and tested for crash recovery; no MCA replacement follows. SIMD/POD casts cannot define byte order or resolve aliases. Allocators must preserve FFI ownership. Read-mostly publication must account for retained generations. Loom checks only instrumented bounded models and does not verify Java/JNI automatically.

## Validation and remaining work

Run `python -B tools/testing/test_external_reuse_ledger.py` from the isolated hardening checkout. The validator checks exact H22.5 name coverage, serious extras, unique records, source/license fields, prototype pins, explicit pending evidence, production constraints and documentation coverage. Negative tests remove required candidates and pins, corrupt license evidence, duplicate identities and inject unsupported completion/authority claims to ensure rejection.

Passing the validator proves inventory structure and coverage only. It does not validate upstream source behavior, license applicability to an unbuilt distribution, benchmark results, runtime compatibility or completion of H22.5's replay, GPU, ECS, JNI, storage and hot-method experiments. Those remain separate implementation/evidence obligations.
