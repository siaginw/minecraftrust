# H17 allocator experiment

Status: isolated executable experiment. No production allocator selection, root manifest change, packet authority, lifecycle authority, or default change. The current production Rust crates do not declare a global allocator; the System lane is the executable baseline. H15 supplies actual Windows process-memory observation and explicit unknown semantics, while this executable adds requested-layout accounting.

Cargo.lock pins all transitive registry versions/checksums. The runner checks every registry archive against its checksum and every extracted file against that archive, preserving package licenses, repository and packaged VCS provenance in the receipt. System-installed rpmalloc discovery is forcibly disabled with `LIBRPMALLOC_NO_PKG_CONFIG=1`. The C compiler, Rust tools and executable hashes are recorded. The operating system and SDK installation remain part of the recorded host, not a hermetic cross-host build claim.

The rpmalloc wrapper calls rpaligned_alloc/rpaligned_calloc/rpfree; its default GlobalAlloc reallocation performs allocation/copy/free. The pinned C preload implementation initializes the process allocator before Rust allocation, initializes threads lazily, and uses Windows FLS destruction to finalize thread caches. Its deferred frees/orphan heaps support freeing allocations after producer exit; controls exercise this exact boundary. The experiment never calls process finalize while Rust allocations may still exist. No malloc symbol override or large-page option is enabled. Initial MSVC linking exposed missing Advapi32 imports in the sys build; the experiment's build.rs supplies that import library only for the rp feature on Windows. The original failure classification is retained separately; no third-party source was patched.

## Workload and ownership

This is an authored mixed-lifetime schedule executing real current kernels, not a replay of a captured server allocation trace. Each publication builds four actual H6 NativeSections from u32 DenseRuntimeStateIds above 65535, retains immutable old dense views, performs 64 edits per section, runs the existing layout maintenance policy, and retains new views. An explicit fixture registry maps only its admitted 1024 IDs to the legacy wire range; subtraction/range checks precede narrowing.

The actual native-chunk encoder produces its strict same-operation mask/length result. Two equal-size zeroed scratch buffers receive the raw payload and unchanged production zlib compression, and a separately owned output copy survives scratch destruction. The Vec lane allocates two independent buffers; the bump lane has a 512 KiB limit and resets only after the owned copy exists. H14 buffer pooling is not silently combined with this comparison. No arena reference escapes; two compile-fail tests reject use after arena destruction/reset. A boxed owned object proves Drop runs; a raw borrowed Drop object is an explicit negative control proving reset does not run Drop. No heap resource is leaked by that negative control.

The same publication inflates a bounded compressed NBT fixture, calls the unchanged H9 strict lossless scanner, changes precisely the eight-byte LastUpdate field, and recompresses through the unchanged backend/level. Fixtures preserve opaque nested mod bytes, raw modified UTF-8 null/unpaired surrogate encodings, NaN payload bits, DataVersion, and NEID values beyond u16. Input fixture construction/compression occurs outside the timed batch. Publication creation, section work, wire adaptation, scratch allocation/zeroing, serialization, compression, NBT inflate/scan/edit/recompress, consumer digest traversal, retention bookkeeping, producer creation/join and final destruction occur inside it. This is an in-memory pipeline: disk/region I/O, JNI, sockets, Java callbacks and server ticks are excluded.

Same-thread and cross-thread lanes use the same publication order, a four-item consumer ring, and retain every fourth publication until the producer has exited. Cross-thread delivery uses a channel bounded to two items. Remaining retained references are checked before final release, every Published destructor is counted, and all final releases occur on the consumer thread. Existing H6 ownership gates are not exercised or replaced by these local fixture Arcs. The consumer retained-payload maximum deduplicates its ring/retained references; it excludes the producer/channel and is not process live memory.

## Correctness and measurement contract

Twelve integration tests plus two lifetime compile-fail tests run separately for each backend with one test thread. They cover exact lane bytes, an independent bit-by-bit packet decoder, independent dense state comparison, exact NBT edit bytes, producer exit before final free, retained views, alignment/zeroing/reallocation, bounded failure rollback and destructor counts. An executable correctness pass verifies four lanes and eight publications per backend, then compares all sixteen compressed artifacts across backends. An additional Job-limited child requests 512 MiB under a 64 MiB process cap using fallible Vec reservation and checks the original buffer remains unchanged.

The first packet divergence is preserved: the authored decoder expected zero skylight while the legacy section constructor defaults to 0xFF when no light is supplied. The fixture now explicitly supplies both all-zero light arrays, preserving the intended test input rather than changing the decoder or production semantics. It was a fixture-assumption failure, not an allocator failure.

The allocation wrapper forwards pointers/layouts unchanged and uses allocation-free atomics. Counts describe successful requested Rust layouts and requested live bytes and an instrumented event-order high-water mark, not exact simultaneous backend live bytes, native backend usable sizes, allocator metadata, direct Windows allocations, or realloc's temporary internal peak. Failed allocation preserves ownership and increments a separate failure counter. Instrumentation runs equally in all lanes but can change relative performance through contention. It is not an uninstrumented production throughput estimate.

Each batch records wall time, Windows process CPU, requested allocated/freed/live/high-water bytes, application retained payload, arena reservation, working set and private commit. Process snapshots are taken after batch final releases and separately after producer exit while the designated long-lived views are still retained; neither is a continuous RSS peak. The common bounded sampling cost is inside the timed pipeline. Windows CPU accounting uses 100 ns FILETIME units with a coarser effective resolution; individual short batches can report zero. An aggregate including visible warmup batches is retained. Process working set is the Windows resident-memory observation; private commit includes allocator caches, runtime state, stacks and other process mappings. `private_minus_requested_live_proxy` is deliberately named a proxy. Pure allocator fragmentation and usable allocation sizes remain unknown; no subtraction is relabeled fragmentation. Job peak commit is a separate process bound/peak, not RSS.

The bounded campaign uses three fresh processes per backend/scratch/delivery lane and six measured batches per process, with three visible warmup batches. Process order rotates between forks. Every raw row remains available. Median and nearest-rank p95/p99 describe only these eighteen observed batches; p95 and p99 both equal the observed maximum at this sample size. No confidence or real-server tail claim follows from this experiment. The runner preserves failed receipts, detects source/tool/executable drift, verifies exact output/count schemas and writes only fresh directories under the isolated checkout target. Native children use the H9 Windows Job helper with one process, 256 MiB memory, 45 seconds and 1 MiB per output stream. Build commands use a separate bounded Windows Job for their complete descendant tree, two Cargo build workers, a 3 GiB total commit limit, 64 processes, 240 seconds and 4 MiB per stream; startup/timeout/output/descendant cleanup controls verify the harness.

Run correctness with `python tools/allocator-experiment/run.py --output target/architecture-hardening/<fresh>`; add `--measure` only in a coordinated performance window. The machine receipt is the authoritative outcome; a successful bounded result still leaves production integration unapproved. A production allocator decision requires captured workload distributions, longer retention/fragmentation observation, uninstrumented end-to-end confirmation, relevant target platforms and live lifecycle integration.

A retained first final-campaign attempt stopped on an overly strict harness assumption: the first cross-thread warmup retained 48 requested bytes although all publication destructors ran, and subsequent batches balanced. The correction checks counter conservation on every row and zero net requested retention for measured steady-state rows. All startup rows and their net retention remain visible with UNKNOWN attribution; this is not declared a leak fix or relabeled allocator fragmentation. The failed final01 receipt remains historical evidence.
