# Bounded observability foundation and offline adapters (H15)

Status: **FOUNDATION_WITH_OFFLINE_ADAPTERS; LIVE_RUNTIME_COVERAGE_INCOMPLETE**. This is a permanent reusable API and a tested integration seam, not a claim that every live server path is instrumented. Nothing here grants optimization, packet, storage, worldgen, or mutable ownership authority. Production gates, defaults, existing H3 metrics/FFI, bridge sources, and MCK6 are unchanged. The crate remains an isolated workspace until coordinated integration.

## Components and coverage

`crates/native-observability` contains fixed enums for 18 duration stages, 16 quantity families, and 12 reasons; bounded HDR histograms; private origin/slot/generation worker leases; quiescent aggregation; a 256-entry optional sampled trace buffer; a real H3 cumulative read adapter; and Windows process memory sampling. Only explicit caller attachment enables a worker. Disabled measurement calls the original body without reading a clock or recording a sample.

`tools/observability/library` is reusable Java 8 code, compiled independently of the offline fixture. `RuntimeTelemetry` measures registered callback invocations with per-thread fixed stacks and inclusive/exclusive totals. `CallbackRegistry` binds actual reflected method and exact runtime receiver identities to passively observed class definitions. `StageBuffer` exports bounded duration batches off the hot path; the Rust importer validates the entire batch before producing HDR results. `MxBeanSampler` reads actual heap and collector MXBeans without converting unsupported values to zero.

The actual offline callback adapter calls the pinned `NoiseGeneratorOctaves.func_76304_a` directly. It obtains the actual Minecraft mod container from the initialized Forge loader, registers the actual method/receiver, and compares 6,800 output doubles by raw bits against unwrapped calls. This is one observed runtime callback, not a server tick or complete generation operation. Fixture owners for nested controls are explicitly synthetic. No mod-name match implies optimization eligibility.

## Identity, lifecycle, and exceptions

Java registry capacity is 64 method bindings and 16 actual owner objects, with at most eight local revocable dependencies per method. Its private token includes registry identity and a monotonic origin; slots are never reused inside that registry. Each method receipt includes full `CANONICAL_ID_V2` semantic and declaration-order hashes, raw final-definition hash, exact descriptor, and an opaque definition-plus-actual-loader observation generation. Runtime checks compare `Class` and loader object identity, not names. An inherited method requires an explicitly bound exact receiver class; an override cannot masquerade as its parent method. The receiver class label in exported JSON is descriptive; the in-memory check uses actual class identity.

The passive observer retains at most 64 selected class definitions of at most 2 MiB each, with weak loader references. Selection by a fixed name filter only limits collection. Admission needs the actual observed class and method. The offline harness loads this observer last among its pinned agent list, after Forge's byte transformations have fed `defineClass`; raw bytes are cross-checked against the independent existing runtime observer. Every redefinition attempt (`classBeingRedefined != null`) and repeated loader/name observation invalidates the old measurement binding and retains a non-admitting tombstone until that loader is collected. Attempted replacement bytes are never published, even if the JVM later rejects them. The observer has no definition-completion protocol and therefore never requalifies a successful redefinition either. A dropped first observation also leaves a tombstone; exhaustion of tombstone storage closes new admission, and an unexpected observer exception invalidates all bindings. This is not proof against an unqualified agent installed later. A new live adapter must bind the complete final transformation order and implement a separately verified completion protocol before supporting redefinition. Metrics do not establish method-effect purity or writer closure.

Local dependency tokens are measurement invalidation handles, **not H4 capability grants**. Export separates registered status from currently valid binding. Late dependency revocation invalidates a completed duration rather than attributing it under stale assumptions. Registry close/revoke clears strong reflected method, receiver class, dependency, and owner references. Neither a digest nor a known method name enables optimization. Both Java and all receipts expose authority as false.

Java collectors allow at most eight attached threads and stack depth 64. Each worker allocates arrays at attachment; hot entry/exit uses those arrays. Attach/detach and export are explicit cold operations. Detach clears receiver/token stack references and removes the thread-local entry. Shutdown requires all workers detached. An abandoned thread can consume one bounded slot; there is no unsafe cross-thread cleanup or claim of automatic cleanup. Snapshots and export/reset require external quiescence; checking stack depth alone does not synchronize against a thread entering immediately afterward.

`call` runs the original body once and returns its exact result or throwable, even when the metrics clock fails. Reflection uses the caller's actual `Method.invoke`, preserving its access checks and `InvocationTargetException` wrapping. A mismatched attribution token never changes the reflection target. Unregistered/foreign/subclass/depth-overflow calls continue original execution while exporting missing coverage; an unobserved child taints parent exclusive-time completeness. Bind/attach/configuration are cold control APIs and may reject invalid configuration before installing any adapter. The callback-body adapter itself must actually invoke the bound method: this library does not prove arbitrary caller-supplied body effects.

Rust worker leases similarly bind private registry origin, slot generation, and an unforgeable shared lease. Foreign close and slot-reuse ABA are rejected. Registry destruction revokes workers. Closing a worker merges its completed histograms only under exclusive Rust borrows. Worker-local last-value gauges do not become a fabricated global instant. Trace entries not exported before closing become counted dropped entries.

## Histogram and batch semantics

HDR is pinned to `hdrhistogram = 7.5.4`, default features disabled, fixed 1 ns through 60 s bounds, three significant digits, and resizing disabled. Zero durations are valid. The API returns a lower/upper bucket interval for integer nearest-rank p1 through p100; tests compare all percentiles with independently sorted data. Empty populations, unknown observations, arithmetic overflow, or a selected rank in the above-range tail return no complete quantile. Values above 60 s retain their true population rank, count and exact maximum; they are never clipped into the last bucket. All missing/lost samples remain explicit unknowns.

No coordinated omission correction is applied. These are distributions of observed operation durations. A missing tick or deadline must be reported separately; the platform does not invent delays for an unknown expected schedule. Quantity event totals are available only for additive per-event deltas. Heap/RSS/queue gauges and cumulative GC samples have last-value observations, never additive resource totals.

`RUSTCRAFT_STAGE_BATCH_V1` uses ASCII TSV: header, at most 4,096 `S <stage-id> <ns-or--1>` records, then at most one `D <stage-id> <lost-count>` per stage. The importer checks a 1 MiB size cap, total/sample capacity, stage range, field counts, integer ranges, negative duration policy, duplicate loss counters and ordering before any successful output. It emits exactly 18 stage results. This is a cold filesystem integration seam, not a new hot JNI call or shared native pointer. Foreign Java producer threads never become concurrent writers to sample arrays; their losses are counted atomically. Reset is permitted only after the consumer has accepted the export and producers are quiescent.

A collector's histogram counter storage is 3,981,312 bytes on the measured configuration, allocated before recording. An aggregate plus eight enabled workers therefore needs about 35.8 MB for these counters, plus bounded metadata/trace storage. This is a deliberate memory cost, not a claim that observability is free. The native executable instruments only its own allocator and checks that 100,000 hot duration/quantity/reason updates allocate zero bytes/events. It never replaces the production allocator. Optional trace sampling keeps 256 coarse events and counts later drops; no every-block tracing is installed.

## Real platform adapters and tool decisions

The [H3 contract](../engineering/ffi-telemetry-v2.md) remains authoritative for JNI units: native body elapsed time excludes the full Java/JNI transition. H15 returns the existing cumulative snapshot and an explicit unknown full-call value; it neither divides cumulative totals into invented histogram samples nor repeatedly adds the same snapshot.

Windows `WorkingSetSize` is the process working set; `PrivateUsage` is private committed memory. Neither equals live Rust allocation ownership. [Microsoft's structure contract](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex) supports these labels. MXBean negative values remain null; GC count/time are cumulative and time is in milliseconds. The cold sampler caps collector rows at 16 and marks truncation. [Java8 memory](https://docs.oracle.com/javase/8/docs/api/java/lang/management/MemoryMXBean.html) and [GC](https://docs.oracle.com/javase/8/docs/api/java/lang/management/GarbageCollectorMXBean.html) interfaces define this coverage. The optional benchmark [ThreadMXBean allocation extension](https://docs.oracle.com/javase/8/docs/jre/api/management/extension/com/sun/management/ThreadMXBean.html) reports approximate Java-thread heap bytes, including sampler overhead; unsupported/disabled values remain null and do not prove native allocation coverage.

The exact published [HdrHistogram source](https://github.com/HdrHistogram/HdrHistogram_rust/tree/a3818d6ce81556010c7f04f423e1fa28a9ff1b5c) is used under MIT OR Apache-2.0. Every dependency archive and extracted file is verified against Cargo.lock in the runner. Its optional serialization/sync features are excluded. [metrics 0.24.6](https://docs.rs/metrics/0.24.6/metrics/) is a future exporter candidate; installing its general string-label facade is deferred until bounded identities are enforced at the exporter. [tracing 0.1.44](https://docs.rs/tracing/0.1.44/tracing/struct.Span.html) is also deferred: subscriber/filter lifecycle and async boundaries require separate integration. No unbounded span labels or exporter are installed.

[Tracy](https://github.com/wolfpld/tracy) (BSD-3-Clause) is a Windows native diagnostic candidate, not installed here. [Samply](https://github.com/mstange/samply) (MIT OR Apache-2.0) supports Windows ETW; Java8 JIT symbol coverage in this runtime is not established, and no broad system-wide capture was run. Current [async-profiler maintained platforms](https://github.com/async-profiler/async-profiler#supported-platforms) list Linux and macOS; no unsupported Windows installation is attempted. Java8 JFR support is tested against the actual pinned Temurin8 runtime instead of inferred from major version: the runner starts a fresh recording, checks its nonempty FLR file, and preserves stdout and its identity. That startup probe is not a server profile.

## Reproduction and evidence

Run `python tools/observability/run.py --output target/architecture-hardening/<fresh-name> --forks 3 --samples 6` from the isolated checkout. `--samples 0` performs correctness only. The runner uses pinned local Java/Cargo tools, sanitizes inherited Java/Rust flags, makes a fresh target, records every subprocess return and output, checks scoped Rust formatting/clippy/tests, compiles Java8 sources, and launches offline FML without a server or world. Inputs, tool binaries, dependency archives/extracted sources, runtime jars, and compiled classes are checked for drift. Failed runs are retained under their original unique target.

Measured modes rotate within each fork: direct, disabled, enabled, direct nested, disabled nested, enabled nested. Bodies and receiver inputs are identical inside each comparable group; result sums must match. Java bodies are preallocated and deliberately use cached integer results for this overhead fixture. Reflection boxing/allocation and arbitrary mod behavior have separate semantics and are not covered by a zero-allocation claim. Java timings retain three warmup groups; native timings use rotating direct/disabled/enabled/existing-H3-body modes with visible raw rows. These are bounded observer-overhead measurements, not server throughput or tail-latency forecasts. The H15 machine receipt carries exact counts and results, keeping this source document independent of its own hash-bound final run.

The first offline run failed because telemetry interfaces were resolved in two defining loaders. That receipt (`h15-dev-01`) is retained. `OfflineEntry` now installs the explicit library loader exclusion before the JVM verifies callback-signature-bearing classes; a fresh run (`h15-dev-02`) passed. This correction is confined to the offline adapter. Do not turn it into an implicit arbitrary mod loader policy.
